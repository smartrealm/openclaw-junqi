# 协作运行时更新与混合 schema 恢复规格

## BUG-01：旧插件失败时仍可受控更新

**当前**：无活动恢复事务时，旧插件的数据库启动错误先于插件版本比较，设置进入不可应用的 `service_failed`。

**目标**：活动恢复事务继续优先处理；其他情况下，probe 确认的插件缺失、版本落后和未加载状态先于能力错误。版本落后进入 `update`，且只有当前目标、连接和桌面所有权均核验后才能应用固定包。

**验收**：

- [x] 旧插件版本与固定包不同时，即使 capability 返回 `DATABASE_SCHEMA_UNSUPPORTED`，仍进入可应用的 `update`。
- [x] 同版本插件返回数据库错误时仍进入 `service_failed`，不得循环重装。
- [x] 活动 health-pending 事务返回数据库错误时仍保留准确回滚入口。

## BUG-02：精确混合 schema 13 安全迁移

**当前**：schema 13 只要包含 `commands_available` 就按未知结构拒绝。

**目标**：允许历史 schema 13 对象集合加定义完全匹配当前权威的 `commands_available`，并沿既有备份和事务路径迁移到 schema 15。其他对象、错误 SQL 或错误列定义继续失败关闭。

**验收**：

- [x] 精确混合 schema 13 迁移到 schema 15，收据和数据完整性保持有效。
- [x] 私有备份保留 schema 13 metadata 和混合索引。
- [x] 同名但定义错误的索引不进入迁移，原库不提交修改。
- [x] 标准 schema 12、13、14 行为不变。

## BUG-03：错误语义不预判回滚

**当前**：办公室把当前插件不支持直接描述为只能恢复安装前状态。

**目标**：无活动恢复事务时，提示核对并更新已加载插件；仅在恢复事务存在时描述回滚。

**验收**：

- [x] 办公室错误信息不再把回滚描述为唯一动作。
- [x] 设置页的旧插件版本优先显示更新动作。
- [x] 数据未迁移前继续明确说明现有数据未被修改。

## BUG-04：插件回滚材料只存在于健康确认前

**当前**：同一插件标识会由 OpenClaw 原位覆盖，但 JunQi 在健康确认成功后仍保留旧插件归档、配置备份和暂存包，状态继续声明可以回滚。

**目标**：旧插件归档只作为当前更新事务的短期失败补偿。真实 Gateway 确认新插件版本、schema 和能力契约后，恢复入口与磁盘制品必须在同一终态关闭；回滚完成并重启目标 Gateway 后也不得保留新包或旧归档。

**验收**：

- [x] 健康确认成功返回 `recoverable: false`，状态查询不再声明可恢复。
- [x] 旧插件归档、配置备份、暂存包和本次事务目录被删除，日志不再保存其路径、摘要或安装来源详情。
- [x] 重复健康确认保持幂等，并可重试上次未完成的安全清理。
- [x] 清理未完成时界面显示独立失败状态，不把插件误报为完全就绪，也不重新提供回滚动作。
- [x] 已确认终态调用恢复接口返回 `BOOTSTRAP_NOT_RECOVERABLE`，不会退回缺少制品的伪回滚路径。
- [x] 安全删除遇到符号链接或目录漂移时失败关闭，不跟随到事务边界外。
- [x] 回滚完成并成功发出目标 Gateway 重启后清理同一事务制品。

## BUG-05：不同插件构建不得共用版本

**当前**：包含 schema 迁移修复的归档仍使用 `0.5.5`。旧 `0.5.5` 启动失败时无法返回能力摘要，客户端把它视为当前构建并禁止更新。

**目标**：任何影响插件代码、数据库迁移或运行契约的变更都必须使用新插件版本。当前固定包使用 `0.5.6`，使旧 `0.5.5` 的数据库启动失败进入受控更新。

**验收**：

- [x] 回归在固定包仍为 `0.5.5` 时得到 `service_failed`。
- [x] 固定包升为 `0.5.6` 后，同一旧插件状态得到可应用的 `update`。
- [x] 包清单、插件清单、运行时常量、两份生成元数据和归档版本一致。
- [x] ARM64 本地测试 DMG 只读挂载确认包含 `0.5.6` 固定归档和一致 metadata。

## 未完成的运行验收

- [ ] 实际协作数据库迁移到 schema 15，私有 schema 13 数据库备份存在且智能体办公室恢复读取。
- [ ] 健康确认后目标机器上不再存在本次插件更新的旧插件归档和暂存包。
