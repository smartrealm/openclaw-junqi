# 协作插件现行 Schema 单一权威整改规格

日期：2026-08-09

## 依据

- 根级 `AGENTS.md` 要求过时实现直接删除，不保留历史迁移、兼容包装或猜测性 fallback。
- 协作插件当前持久化契约由 `packages/junqi-collab/src/schema.ts` 的
  `SCHEMA_VERSION` 与 `SCHEMA_SQL` 定义。
- 删除、导出和外部写命令的恢复事实必须来自可核验的持久化身份，不能根据旧路径、同 Run
  候选行或缺失回执推断。

## 当前问题

1. 数据库构造会先执行现行建表语句，再逐版本迁移已有库；新库与升级库可能形成不同结构，且旧字段
   回填依赖推断。
2. 删除命令同时写入统一回执和删除专用回执，启动时还保留冲突隔离表，形成多个幂等权威。
3. 导出制品读取接受绝对路径并尝试按文件名重映射，可能把历史宿主路径继续解释为当前受管制品。
4. 删除墓碑缺少作业引用时会按同 Run 的候选作业数量收养或猜测恢复所有者。

## 目标行为

1. 新空库仅从现行 Schema 创建，并写入现行版本与稳定实例身份。
2. 已有库必须同时满足精确版本和结构形状；版本缺失、版本不同或结构漂移时，在任何写入前失败，
   原库保持不变。
3. `command_receipts` 是外部写命令唯一的回执权威；不存在删除专用回执、冲突隔离表或历史重建路径。
4. 受管导出只接受有界 JSON 制品标识，不接受绝对路径或路径重映射。
5. 显式删除墓碑必须绑定唯一的 `deletion_job_id`；只有 `retention-policy` 墓碑可无删除作业。
6. 恢复只使用墓碑记录的精确作业身份；缺失、错配或矛盾事实进入 `PARTIAL` 并保留证据，不收养候选作业。

## 验收条件

- 新库重开后实例身份稳定，外键开启，结构与 canonical Schema 完全一致。
- schema 13、schema 15、无 metadata 和现行版本结构漂移均确定性失败，且版本及原始表不被改写。
- 删除重放只由统一回执完成；缺失权威回执时返回 `IDEMPOTENCY_CONFLICT`。
- 绝对导出路径导致对应导出作业失败，引用文件不移动、不删除。
- 显式删除墓碑无作业引用时由 SQLite 约束拒绝；错误作业引用和持久化矛盾均失败关闭。
- 协作插件 TypeScript、定向测试、完整测试、包校验和生成 bundle metadata 均通过。

## 未验证边界

- 不支持把旧 Schema 数据自动转换为 schema 14；现有非当前库会拒绝启动并要求由明确的数据处理流程处置。
- 尚未在真实最新版 OpenClaw Gateway 上执行插件冷启动、数据库替换和删除中断恢复。
- 尚未在 macOS、Windows 和 Linux 真机验证 SQLite 文件权限、断电语义和目录同步行为。
