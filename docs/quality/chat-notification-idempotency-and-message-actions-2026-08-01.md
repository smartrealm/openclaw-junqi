# Chat 通知幂等与消息操作栏修复

## 依据

Gateway 的流式终态和持久转录都需要保留：前者负责流式 UI 收尾和通知，后者负责重连和离线转录恢复。通知身份只能使用上游明确提供的运行身份，不能由 JunQi 推断。

## 当前行为

`App.tsx` 曾让流式终态和持久转录两条路径各自调用通知服务。OpenClaw 的 `session.message` 广播不带 `runId`，JunQi 因而以消息 ID、正文和时间窗口推断关联，造成重复通知风险。助手消息的预览与复制按钮位于绝对定位容器，短气泡内容可能被按钮遮挡。

## 目标行为

- 聊天通知只接受 OpenClaw `chat` 流式终态的 `sessionKey + role + runId`。`runId` 缺失时不发布通知；持久 `session.message` 与通用 `onMessage` 只更新会话状态，不参与通知。
- 前端通知服务在当前进程内拒绝重复键；Tauri 持久层使用同一精确键拒绝跨重连、跨窗口刷新造成的重复写入，并向 renderer 返回是否实际插入。声音、Toast 和后台系统提示只在新增记录后呈现。
- 通知仓库不再按消息 ID、正文或时间窗口推断不同事件是否相同；历史记录也不执行此类迁移。
- 通知中心读取、实时推送、终端工具生命周期写入、已读和清空均经由 `persistentNotificationRepository` 的 typed command 边界；组件不直接拼装通知 IPC 载荷。
- 缺少原生 `runId` 或没有可见正文的流式聊天事件不发布通知；非聊天通知仍可作为独立事件保存。
- 助手消息的预览和复制操作栏在气泡内正常排版，保持现有 `ChatIconButton` 的多语言 Tooltip，不能遮挡正文。

## 验证

- TypeScript 单测覆盖只从流式终态的原生 `runId` 生成幂等键、通用回调和持久转录不发布通知，以及缺失身份或空正文不发布边界。
- Rust 单测覆盖相同键只保留一条、无键事件仍保留两条。
- 通知命令契约测试覆盖通知仓库为唯一 renderer IPC 出口，终端可见时的自动已读仍通过该出口执行。
- 仍待桌面真机验证：流式终态与持久转录同时到达时只出现一次提示；持久转录本身不会发布系统或应用内通知。
