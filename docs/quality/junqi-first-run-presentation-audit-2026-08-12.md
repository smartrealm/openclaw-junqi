# JunQi 首次设置页面稳定性审计

## 审计范围

本次审计以用户提供的 `/Users/wei/Desktop/流程.gif`、当前 JunQi 首次配置实现、
`docs/design/` 中的交互规范，以及 2026-08-12 拉取的 OpenClaw 官方主线
`1da8fffbc` 为依据。审计覆盖欢迎、环境检测、存储、运行方式、依赖安装、Gateway 启动、
OpenClaw Wizard 和完成页。目标是修正页面重复、空白和切换闪动，不改变原生安装事务或
OpenClaw Wizard 的步骤、答案、终态与渠道插件语义。

## JunQi 安装链路事实

- 首次设置的所有页面都通过共享 `SetupShell` 呈现，顶部五步进度和底部操作区属于同一窗口骨架。
- 环境探测、存储迁移、依赖安装、Gateway 启动和 Dashboard 进入均已有真实 loading 或操作状态；
  页面只能投影这些状态，不能用定时器、假百分比或乐观成功填补空白。
- 存储应用期间是原生单飞事务，界面必须锁定旧表单并呈现真实迁移进度；完成状态仍允许用户显式
  返回更改位置，不能让已失效的表单修改绕过再次保存。
- 安装进度与日志来自 Tauri 事件，运行方式和环境能力来自真实探测。布局统一不能合并这些状态机。

## 官方契约

- OpenClaw `WizardSessionPrompter` 将 `note`、`progress`、`action`、`select`、`text`、
  `confirm` 和 `multiselect` 作为结构化步骤交给客户端呈现。
- `outro` 会先产生标题为 `Done` 的 `note`。该提示仍需客户端确认；只有随后
  `wizard.next` 返回 `done: true`，官方会话才进入终态。
- Gateway executor 的 `progress` 不等待用户答案，客户端只轮询下一步；client executor
  的步骤必须按当前步骤 id 提交，不能本地跳过或合并。
- JunQi 只负责忠实呈现当前结构化步骤、真实提交活动、日志和错误。短步骤也不能被改写成
  客户端自定义流程，渠道授权结果仍由官方 Runtime 或插件拥有。

## GIF 中的可复现问题

1. 环境检测、存储、安装与 OpenClaw 配置使用同一步进器，但部分页面自然增高、部分页面固定高度、
   安装页使用宽布局，切换时标题和主体视觉重心不一致。
2. 存储读取失败、Git 缺失、Node.js 缺失和 Gateway 启动页面会在页面标题与主体状态卡中重复相同标题；
   存储应用期间旧表单仍留在页面，主要反馈只出现在按钮和表单底部。
3. 配置核验、QuickStart、渠道选择、渠道授权、Gateway、网页搜索和 Done 都位于顶部
   “配置 OpenClaw”阶段，但主体容器在短提示、长列表和二维码之间反复改变高度。
4. `note`、`confirm`、`progress` 和 `action` 已在主体显示官方 message，页面副标题却退回
   全局配置说明，造成同一阶段的泛化说明反复出现，信息层级不清楚。
5. 短提示只占一行卡片，页面剩余区域完全空白；长列表和二维码又立即撑高内容，视觉重心
   在每一步之间大幅移动。
6. `SetupShell` 用 `contentIdentity` 作为 `main` 的 React key，官方步骤变化会重建整个主体。
   标题、内容和滚动容器同时卸载，容易出现闪白、滚动复位和页面跳动。
7. 只有环境探测与配置核验使用稳定运行时容器，其余设置页退回自然高度；同一首次设置流程存在
   两套几何边界。
8. 只有授权提交会替换成等待卡片。QuickStart、Gateway、网页搜索和 Done 提交时仍保留旧
   内容，仅底部按钮旋转；尤其 Done 会被误读为已经完成，而真实 `done: true` 尚未返回。
9. 日志展开会继续增加卡片与页面总高度，使状态更新推动外层布局。
10. 环境检测的 OpenClaw、Gateway 与 Docker 探针分两条异步路径运行。页面会先进入环境复核，
    再由 Docker 探针补写结果；同时 `detecting` 与 `environment-review` 使用不同组件和视觉场景，
    一次正常数据收敛会触发整块主体重挂载、场景位移和卡片内容二次变化。
11. 欢迎、探测和复核合并为常驻组件后，欢迎页的前进单飞锁也会跨阶段保留；返回欢迎页若不显式
    复位，第二次点击“下一步”会被误判为重复提交。

## 目标行为

- 欢迎、检测、存储、运行方式、安装、Gateway、配置与完成页共享同一窗口自适应内容框架；
  标题区、内容区和底部操作区保持稳定，内容与日志只在主体内部滚动。
- `main` 不再按步骤卸载。步骤切换只在稳定内容区内使用短时透明度和轻微纵向位移，系统启用
  减少动态效果时立即切换。
- 存储读取、恢复、应用和已就绪状态使用共享状态面板。应用期间旧表单退出交互，进度只来自真实
  存储事件；已就绪状态提供明确的继续和更改位置操作。
- Git、Node.js 和 Gateway 的页面标题表达“运行时”阶段，具体错误或活动只在状态面板中出现一次。
- 官方标题与 message 各只呈现一次。标题缺失时使用 JunQi 的阶段标题；message 位于表单说明
  或步骤主体，不用全局副标题重复填充。
- 短提示、确认和文本输入使用同一最小内容高度与对齐方式；长列表和授权二维码仍呈现完整内容，
  但不改变外层高度。
- 任意步骤提交后立即进入由 `wizardSubmitting` 或 Gateway progress 驱动的真实等待态。Done
  提交后明确等待官方终态，不把 note 当作完成。
- 错误只在一个状态面板中呈现，不同时保留旧步骤卡片；恢复操作仍遵循现有 session、runtime 和
  terminal-unknown 围栏。
- 环境探测与复核复用同一个页面组件、视觉场景和三项能力卡骨架。探测中只显示固定 loading，
  OpenClaw、Gateway 与 Docker 全部收敛后一次性替换真实结果；返回复核页仍不自动重跑探测。
- 主体滚动容器保持同一 DOM 节点，步骤变化时通过引用在首次绘制前复位滚动，不再使用 React key
  放大正常状态更新。
- 返回欢迎阶段时同步释放该阶段的前进单飞锁，保持“下一步、上一步、再下一步”可重复执行。

- 本轮不改变 Tauri 安装、存储迁移、Gateway 生命周期、OpenClaw RPC、Wizard session、渠道插件轮询
  或完成门禁。
- 浏览器辅助验收已覆盖 1497×820、720×680、亮色、暗色和键盘焦点；它只能证明页面几何、主题和
  WebView 交互样式，不能替代 Tauri IPC 与桌面安装事务。
- macOS Tauri 开发版已实测环境检测完成页，窗口中的标题、主体和操作区保持稳定；当前自动化宿主
  虽没有 macOS 辅助功能权限，但已通过 CoreGraphics 事件完成欢迎页到环境复核的当前应用内点击；
  后续原生步骤仍未自动验收。
- 系统减少动态效果只完成纯函数与样式契约验证；macOS 完整点击流程、Windows 与 Linux 仍需目标
  平台验证。

  横移或 Docker 晚到后的二次布局变化。
