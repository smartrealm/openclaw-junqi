# Gateway 管理员权限升级链路审计

## 审计结论

审计依据已在 2026-09-14 更新到 OpenClaw 官方主线提交
`87891ce2b5c8e7c72f4a8a722d73669f2e221004`，重点核对
`docs/gateway/operator-scopes.md`、`packages/gateway-client/src/scope-upgrade.ts` 和
`src/gateway/server-methods/device-scope-upgrade.ts`。官方
`src/cli/devices-cli.runtime.ts` 同时明确禁止当前设备批准自己的 scope upgrade，必须由
Control UI 或另一台已授权设备完成批准。

OpenClaw 对 `sessions.patch` 采用参数级权限：会话组织字段和单会话模型使用
`operator.write`，thinking、fast、verbose、trace 和 reasoning 等运行参数使用
`operator.admin`。JunQi 对这两类写入的分流与官方契约一致。

## 缺陷

### BUG-01：管理员拒绝后没有进入官方设备权限升级协议

严重级别：P1。

当前特权连接收到结构化 `MISSING_SCOPE` 后立即拒绝原业务操作，只发布一个恢复界面事件。
恢复界面没有调用官方 `device.scopes.requestUpgrade` 和 `device.scopes.waitUpgrade`，因此拿不到
当前设备的待批准请求，也无法接收批准后轮换的设备令牌。界面建议用户重配或重试，但代码没有
建立可继续原操作的状态链路。

影响范围不是会话设置单一入口，而是所有经统一特权请求器发起的管理员写入。

### BUG-02：业务通知泄漏底层英文授权错误

严重级别：P1。

`useSessionRuntimeSettings` 对未知错误直接显示 `Error.message`。由于 BUG-01 让管理员拒绝直接返回，
通知最终显示 `missing scope: operator.admin`。这既不是可操作的本地化说明，也错误暗示保存流程已经
结束，而全局权限恢复界面可能同时存在。

### BUG-03：轮换设备令牌被同时放入共享密钥字段

严重级别：P1。

JunQi 在没有共享密钥、仅使用已配对设备令牌时，同时发送 `auth.token` 和 `auth.deviceToken`。
OpenClaw 官方 Gateway 客户端只把显式共享密钥放入 `auth.token`，设备凭据只放入
`auth.deviceToken`；两者虽然都参与签名，但属于不同认证通道。该偏差使管理员权限批准后的重连先
触发一次错误的共享密钥探测，后续钉钉管理员操作可能再次进入缺权恢复。

### BUG-04：批准后的令牌验证丢失批准范围并重复使用失效令牌

严重级别：P1。

官方客户端会把 `waitUpgrade` 返回的设备令牌与批准权限集合一并用于重连。JunQi 原实现只保存设备
令牌，随后仍按日常最小权限握手；若 Gateway 返回结构化 `AUTH_DEVICE_TOKEN_MISMATCH`，普通重试又会
继续使用相同失效令牌。结果是用户已经批准，客户端却再次显示权限申请界面。

### BUG-05：桌面客户端冒用官方浏览器控制台身份

严重级别：P1。

JunQi 的 Gateway 握手把 `client.id` 写成了只供官方浏览器 Control UI 使用的
`openclaw-control-ui`。OpenClaw 会把该身份的设备令牌绑定到共享认证代次，而 JunQi 的 Tauri
桌面生命周期并不符合浏览器控制台的认证模型。scope upgrade 批准并轮换令牌后，下一次管理员连接
会被 Gateway 判定为设备令牌不匹配或权限不足，用户因此回到同一个授权弹窗。

### BUG-06：所选 Runtime 的恢复重连误用首次信任凭据

严重级别：P1。

连接管理器用同一个布尔状态表示首次设置启动和后续所选 Runtime 重连。插件安装、Gateway 进程恢复
或官方配置交接触发后者时，目标解析器仍按首次设置规则跳过已持久化设备凭据，强制读取共享凭据。
因此 Gateway 设备列表能证明管理员批准已经生效，当前主连接却没有消费轮换后的管理员设备令牌；
下一次临时管理员连接继续收到结构化缺权拒绝，界面再次显示相同授权弹窗。

此外，共享凭据握手收到 Gateway 返回的设备令牌后，连接目标仍同时保留共享凭据。统一特权请求器
复制该目标时会继续选择共享认证通道，从而再次绕过刚签发的管理员设备令牌。

### BUG-07：已失去原操作的授权提示在重连后不会收敛

严重级别：P1。

主连接成功重连时，旧实现只有观察到一个进程内批准标记才会唤醒特权请求器。该标记与真实等待操作
不是同一个事实来源，批准回调、插件安装对话框和 Gateway 重启发生竞速后，标记可能不存在，而
`scope_denied` 提示会被刻意保留。此时官方设备列表已经没有待批准请求，插件也已经安装，用户仍会
看到同一权限弹窗并被要求再次批准。

首次改为查询真实等待操作时，界面收敛条件又写反：没有等待操作时保留旧提示，存在等待操作时反而
关闭提示。真机复现证明这会让批准后的旧弹窗稳定重现。最终状态转换改为纯函数并增加双向行为回归：
没有等待操作必须清除旧提示，存在等待操作才保留提示并等待原操作真实成功。

### BUG-08：权限升级失败终态重新显示成首次申请

严重级别：P1。

权限申请被拒绝、过期或恢复失败后，恢复界面仍使用首次申请的“请求所需权限”文案。真实终态只藏在
折叠的技术详情中，用户无法区分“尚未申请”和“刚才申请失败”，容易再次进入同一个授权循环。

修复后，三种终态在主操作附近显示本地化错误，并明确说明原操作没有执行；按钮改为“重新请求权限”。
技术错误仍只在用户主动展开的其他方式中呈现。

### BUG-09：普通后台能力探针误触发管理员授权弹窗

严重级别：P1。

目标 Gateway 日志证明，重复错误来自每 15 秒执行一次的
`junqi.collab.capabilities`，而不是用户刚批准的管理员业务操作。当前 Gateway 没有加载可选协作插件；
OpenClaw 对未分类的未知方法按默认拒绝策略要求 `operator.admin`，因此日常主连接得到结构化
`MISSING_SCOPE`。App 原实现把主连接与临时特权连接的 scope 拒绝都送入同一个批准界面，导致用户
批准成功后，后台探针仍按日常权限再次请求并重新弹窗。

修复后，只有统一临时特权请求器的 scope 拒绝可以进入权限升级界面；主连接的 scope 拒绝保留给原
调用方处理，不能伪装成可通过再次批准恢复。协作能力探针在同一已核验连接收到结构化 scope 拒绝后
停止周期重试，只在连接身份换代后重新核验；它不把拒绝推断为插件已安装、已缺席或请求成功。

## 目标链路

1. 日常连接继续只申请日常最小权限，不把管理员权限永久加入普通 Chat 连接。
   JunQi 使用 OpenClaw 正式注册的通用 `gateway-client` 身份和 `ui` 模式，不再冒用官方浏览器
   Control UI 身份。
2. 特权连接收到结构化 `MISSING_SCOPE` 后暂停原操作，并发布统一权限恢复状态；管理员写入申请
   `operator.admin`，其他专用连接只申请 Gateway 明确返回的缺失权限。
3. 用户在恢复界面明确请求管理员权限后，当前已核验主连接调用官方权限升级 RPC。
4. JunQi 创建请求后直接打开官方 Control UI 的 `/settings/devices` 设备审批页，并展示 Gateway 返回的
   准确请求标识；当前设备不再调用本地 `devices approve` 尝试自我批准。另一台已授权设备仍可按准确
   请求标识完成批准。
5. `waitUpgrade` 仅接受相同请求标识的结构化终态。批准时先把轮换设备令牌写入当前 Gateway
   端点绑定的系统凭据作用域，再清除共享令牌优先级，并用批准权限集合验证设备令牌。验证成功后
   恢复日常最小权限连接；只有最终日常连接完成身份核验后才继续原操作。
   后续普通启动也优先恢复该端点绑定的设备凭据；仅首次设置和用户显式 token 输入继续使用
   当前请求指定的共享凭据。
   握手时共享密钥只写入 `auth.token`，设备凭据只写入 `auth.deviceToken`，不得把设备令牌镜像到
   共享密钥字段。
6. 新主连接完成运行时身份核验后，统一特权请求器重新捕获连接身份并重放尚未发送的原 RPC。
7. 拒绝、过期、取消、身份换代、令牌保存失败和协议不可用均保持失败语义，不伪造成功。
8. 若 Gateway 结构化返回 `AUTH_DEVICE_TOKEN_MISMATCH`，删除的范围只限当前端点绑定的设备凭据；
   仅允许同一已选 Runtime 的共享凭据重新签发一次设备令牌，再重复上述验证与日常权限恢复。无法
   证明同一 Runtime 或无法取得共享凭据时停止，不循环使用失效令牌。普通启动读取到失效设备令牌
   时也执行相同的同 Runtime 恢复，但只请求日常最小权限。
9. 所选 Runtime 连接必须区分首次信任和恢复重连。首次设置启动使用当前所选 Runtime 的共享凭据；
   后续配置交接、进程恢复和插件安装重启先读取已批准设备凭据，仅在不存在设备凭据时才回退同一
   Runtime 的共享凭据。共享握手返回设备令牌后，内存连接目标立即清除共享凭据，后续临时管理员
   连接只继承设备凭据。
10. 每次已核验主连接完成后直接查询统一特权请求器的等待状态。若原操作仍在等待，立即触发一次
    重试并保持提示，直到该操作真实成功；若没有等待者，清除旧 `scope_denied` 提示。界面状态不再
    依赖独立的进程内批准标记。
11. 权限申请被拒绝、过期或恢复失败时，主界面显示准确终态和重新申请入口，不再回退为首次申请
    文案，也不暗示原操作已经执行。
12. 普通主连接的 `scope_denied` 不进入管理员批准界面。后台可选能力探针在同一已核验连接收到该
    结果后停止周期重试，等待连接身份换代；真实管理员操作仍只能经统一临时特权请求器申请权限。

## 验证边界

自动化测试覆盖协议字段校验、设备令牌先存后重连、主连接身份围栏、原业务 RPC 只在新授权连接
认证后发送、批准范围验证、失效令牌单次重新签发，以及底层授权错误不再泄漏为会话设置通知。当前机器不作为目标环境证据；macOS、
Windows 和 Linux 的真实系统凭据库授权、远程 Gateway 审批与安装包交互仍需目标平台实测。

2026-09-14 用户在当前源码的新 Tauri 启动代次完成官方批准后仍复现。目标设备列表证明待批准请求为
零，设备和当前令牌均包含 `operator.admin`；目标 Gateway 日志进一步把重复来源精确定位为
`junqi.collab.capabilities`，其失败按 15 秒周期出现。修复普通主连接提示入口和协作探针收敛后，重新
启动当前源码并观察两个完整轮询周期，目标 Gateway 日志没有再出现该方法的 `MISSING_SCOPE` 或其他
新增管理员权限错误。当前只完成目标 macOS 启动与日志链路验证，亮暗主题、窄窗口及 Windows、Linux
真机视觉仍未验证。
