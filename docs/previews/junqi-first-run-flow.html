TRUST MODEL

安装完成遵循官方配置终态

  • 必须验证选定 Gateway 的运行模式与身份
  • 必须完成认证或管理员配对
  • 默认使用官方 Guided 探测与真实模型核验；Classic 只作为显式详细配置入口

PERSISTENCE

两类持久状态

  • Rust Bootstrap：目录、runtime、迁移事务
  • Renderer localStorage：setup-done 与 UI 偏好

INSTALL LATENCY

最短安全等待

  • Node release index 与 checksum authority 并发解析
  • 现有环境、npm cache 与 SHA-256 验证的 runtime 下载缓存优先复用
  • Windows x86 复用稳定 MinGit fallback，缺失才下载；完整性与事务门禁不省略

RECOVERY

失败与重装残留保守恢复

  • 目录事务与运行模式切换可恢复或回滚
  • Windows 半安装只有在 Scheduled Task / 登录项不存在、目标端口空闲、无 managed child 且无 pending recovery 时继续
  • 残留服务、未知监听或探测失败均不停止、不覆盖，先恢复 OpenClaw 后执行官方所有权验证

系统架构检测与 Native / Docker 运行方式确认

安装包先与 Windows 架构匹配；首次启动后 Rust 根据编译目标自动得到 windows/x86、windows/x86_64 或 windows/aarch64，无需用户选择架构。x86 自动进入 Native-only：复用或下载 win-x86 Node.js（npm 随 Node 提供）与 32-bit MinGit，并禁用无意义的 Docker 探测。x64/ARM64 可继续确认 Native 或 Docker。等待时间策略为：并行执行互不依赖的只读检测，优先复用已验证环境与安全缓存，缺失才下载、损坏才修复；最终仍合并到同一个 Gateway 验证门。

代码已修复 · NATIVE SERVICE REUSE

同配置 Native 服务不再被误判为 Docker 冲突

  • Native 切换前若共享端口已响应 selected config/token，且没有 JunQi managed Docker 容器拥有该端口，则保留现有 endpoint
  • 随后仍由 Native 启动链执行健康、token/config 与官方 service ownership 验证；验证失败继续 fail-closed
  • 未知 listener、foreign config 或真实 managed Docker owner 仍不得绕过端口门禁
  • Rust 全量测试、Docker 聚焦测试、TypeScript/lint 与本地 ARM64 production build 已通过；真实首次设置重试仍待人工验证

WINDOWS x86 · 32-BIT

自动走 Native-only

  • ARCH=x86，不需要用户选择
  • Node release catalog 自动选择 win-x86 兼容版本，npm 随 Node 提供

  • Native 使用 win-x64 Node 与 64-bit Git

  • Native 使用 win-arm64 Node 与 ARM64 Git
  • Docker 可用性以真实 ARM64 Docker 环境探测为准

Gateway、配对权限与官方 Wizard

Windows UAC 与 Gateway 管理权限是两套系统。首次设置先关闭旧连接，再按所选 Runtime 的正式配置建立新连接；只有新连接的 hello-ok 围栏与 Runtime Identity 同时核验通过才进入官方 Wizard。Wizard 终态后还要等待活动配置修订收敛，并在同一已核验连接和同一修订上完成最终核验。身份围栏、临时 admin RPC、取消锁和过期响应门禁已经过代码与自动化测试，但尚未在真实 Windows + OpenClaw Gateway 配对环境验证。

FULL FIRST-RUN PRESENTATION

JunQi 安装与官方 Wizard 共用稳定页面骨架

  • 欢迎、环境检测、数据位置、运行方式、依赖安装、Gateway 启动、OpenClaw 配置和完成页复用同一页面骨架；标题区与底部操作区保持稳定，页面主内容区统一滚动，步骤卡片按真实内容自适应且不预留固定高度或滚动槽，日志正文和官方长选项只在确有需要时局部滚动
  • 数据位置的真实目录读取沿用最终表单的静态骨架，不把短暂 IPC 阶段渲染成独立状态页；读取完成后始终停留在表单，由用户点击“下一步”，只有原生存储事务成功才进入运行时
  • 选择当前目录且没有运行时位置、配置路径或恢复状态变化时，只提交布局，不要求尚未安装的 OpenClaw 核验 Gateway 服务；真实迁移和服务绑定变化继续严格核验
  • 数据位置提交期间保留同一表单和内容标识，只锁定交互并在主操作显示真实忙碌状态；不显示客户端自造百分比，也不插入额外进度页
  • 数据位置页默认展开“安装位置”，直接展示工作区及可选 npm、Node.js 和 Git 位置；用户在当前设置会话中的显式折叠选择由设置草稿保留
  • 主体不再按步骤 React key 整体卸载；用户前进时正文从左向右短距离切换，返回时从右向左切换，后台运行状态只淡入；全部过渡为 120 至 180 毫秒且只使用 transform 与 opacity，系统减少动态效果时立即完成
  • 环境探测与结果复核复用同一个场景和三项能力卡骨架；OpenClaw、Gateway 与 Docker 探针全部收敛后一次性发布真实结果，避免 Docker 晚到造成二次跳动
  • 存储失败和恢复使用统一状态面板；成功后直接切换阶段，不增加“数据位置已就绪”页面；国际化资源加载拒绝同一路径的对象与字符串类型冲突
  • 普通步骤的调试日志默认收起；依赖安装在桌面宽窗口左右并列执行时间线和执行记录，窄窗口才使用二选一切换，步骤变化和失败不擅自切换用户视图
  • Gateway 认证连接与运行时身份核验完成后，原地把当前执行摘要替换为已核验状态；内部 gateway-ready 不生成独立页面，用户从同一页面核验配置后才进入官方配置阶段
  • 首次设置启动 Gateway 前关闭旧 WebSocket，并忽略普通设置中保存的手工地址；新连接必须绑定当前所选 Runtime 的配置目标，不能用上一连接的 connected 状态推进页面
  • 官方配置终态导致连接失效时，交接重连重新解析当前所选 Runtime 的端点和凭据，不复用历史连接目标
  • Git、Node.js 和 Gateway 前置条件以“运行时”阶段标题承载，具体活动或错误只在主体状态卡出现一次，避免标题与正文重复
  • 安装、探测和 Gateway 生命周期语义不变；统一的是几何边界、状态反馈和切换节奏，不增加假步骤、假进度或乐观成功

UNIFIED CONFIGURATION STAGE

Gateway 就绪后从同一运行时页面核验配置

  • 运行时步骤完成后仍停留在运行时阶段，原地显示 Gateway 已核验和“核验配置”操作；只有 Guided 可操作状态或 Classic 首个官方步骤返回后才一次激活“OpenClaw 配置”，配置页不再显示连接占位卡后自动跳变
  • 请求 openclaw.setup.detect 协商模式：成功时使用 Guided，明确 unknown-method 时进入官方 Classic Wizard
  • 连接、权限与响应错误不会触发模式切换；支持 Guided 的 Runtime 仍可由用户显式选择详细配置
  • 运行时核验状态只原地更新摘要，正式配置步骤进入稳定配置内容槽；不能生成重复完成卡片或因上一状态滚动出现空白视口
  • 普通 note、action 和 progress 使用同一紧凑摘要，界面只补充官方提示、待执行和处理中层级，上游标题与正文保持原样且只出现一次
  • 官方 outro 仍是需要确认的正式 note；JunQi 只有收到后续结构化 done 才进入完成交接，不从“Done”文字猜测成功
  • 普通交互步骤默认收起日志，日志不参与业务状态推断
  • 官方步骤返回结构化 externalUrl 时由共享组件生成本地二维码、浏览器入口与复制操作
  • 授权步骤提交后立即销毁旧二维码；插件拥有扫码轮询、过期与终态，JunQi 不从扫码表象推断成功
  • 供应商流程结束后重新探测候选并执行真实激活，不把授权结束当作模型可用
  • Guided 与 Classic 终态共用单一交接门禁：重新解析所选 Runtime 连接目标，要求活动配置修订已经应用，并把最终 Runtime、模型和修订核验绑定到同一已核验连接
  • 普通等待超时只保留待核验；只有官方配置或健康响应结构化证明重载关闭时，统一 Gateway 生命周期才补发一次重启

Native 启动前的共享端口门禁现在区分“managed Docker owner”与“已接受 selected config/token 的非 Docker endpoint”。后者保持运行并交给 Native 启动链继续执行 token/config、健康与 service ownership 验证；未知端口占用、foreign config 和真正的 Docker owner 仍按原契约 fail-closed。自动化与本地 ARM64 构建通过，待用首次设置界面重试验证完整日志和页面推进。

代码已修复 · SETUP CONNECTION GENERATION

旧连接不能证明本次所选 Runtime 已就绪

首次设置启动前主动关闭旧 WebSocket，连接动作忽略普通设置保存的手工地址并重新解析当前所选 Runtime。页面只接受新连接的 hello-ok 围栏与 Runtime Identity 核验；正式目标读取失败进入统一错误态，不猜测默认端点，也不再形成未处理 Promise 或伪成功。

代码已修复 · READY NAVIGATION

后台自启动偏好不再困住已就绪用户

官方 Wizard 终态与 Gateway 已验证 Ready 后，自启动交接继续显示真实进度并锁定返回操作，但不再禁用“进入仪表盘”。进入动作重新验证 selected Gateway，并消费同一次流程已取得的官方终态；后台偏好操作不能绕过完成门禁。

代码已修复 · WIZARD HANDOFF FENCING

过期 Wizard 完成任务不得提交交接结果

official-service handoff、交接后 Gateway probe 与连接目标刷新之后均重新验证同一 Wizard operation identity。页面返回或新操作接管后，旧任务即使完成 Rust 交接，也不得修改设置 UI、进入 Ready 或继续后续探测。待 Windows 官方服务交接真机实测。

代码已修复 · ACTIVE CONFIGURATION FENCE

Gateway 健康不能替代活动配置修订与连接身份

官方 Wizard 终态后，JunQi 在同一已核验连接上等待 configRevisionHash 与 appliedConfigHash 非空且相等，并在进入 Ready 前再次核对同一修订。普通超时不抢跑重启；只有官方结构化状态明确重载关闭时才通过统一生命周期补发一次。生命周期屏障记录真实重启尝试代次，恢复内部或屏障之间已经发生过重启时不会再次补偿。身份核验等待期间 socket 关闭或换代会作废待定身份，特权写请求在发送前也会重新核对来源连接。

代码已修复 · CONNECTION RETRY OWNERSHIP

连接轮次、退避和配对取消不再各自为阵

Gateway Manager 只管理连接轮次，Connection 独占 WebSocket 尝试、退避与耗尽；进程健康观察不再并发创建第二轮连接。显式同目标连接先结束旧传输再建立新轮，普通配对取消通过 Manager 同时覆盖活动握手与等待定时器，取消后只有显式恢复才会重新连接。

代码已修复 · WIZARD TERMINAL RECOVERY

未知终态不再被伪装成完成或仍需配置

官方 done 结果单独进入不可重放的恢复边界。首次设置的 Classic wizard.start 先向主线提交 installDaemon: false；stable 在创建会话前精确拒绝该字段时，改用公共参数启动一次，daemon 选择继续由官方 Wizard 步骤拥有。首次消费终态只执行一次服务交接；客户端优先复用当前已核验连接，连接失效时才重连。若最终 wizard.next 返回前原 sessionId 仍因外部原因被回收，确认不可恢复后保留终态未知，不构造本地 done，也不自动调用 wizard.start。用户显式重新开始时还需通过可取消的二次确认，并获知可能重复配置写入的风险。授权步骤提交期间旧二维码会替换为等待投影，超时和终态继续由官方插件拥有。正式步骤的旧正文退出后才进入新正文，前进与后退不再叠放内容。

代码已修复 · RUNTIME CREDENTIAL / PROBE FENCING

同端口 Native/Docker 不再共享设备凭据或完成条件

后端为 selected runtime/config 输出非敏感 credential scope；设备 token 的预认证存储键绑定 scope + endpoint，Native 与 Docker 即使共用 127.0.0.1:18789 也不会读取对方 token，且 selected runtime 不再回退到无 scope 的旧 endpoint 凭据。Wizard 完成只消费同一次官方会话返回的终态。待真实配对和切换竞态实测。

代码已修复 · ATTESTED CREDENTIAL PROMOTION

endpoint alias 已指向 instance 后，Gateway 返回的新 device token 不再回写 selected-scope 或裸 endpoint slot，而是写入当前 durable instance key；避免下一次 promotion 用旧 instance token 覆盖新 token。已通过源码契约测试，待真实 Gateway token rotation 实测。
