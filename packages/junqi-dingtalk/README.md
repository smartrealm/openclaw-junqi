# JunQi DingTalk Business Plugin

This OpenClaw plugin exposes a fixed DingTalk business tool set backed by the DWS command line runtime.

The Gateway owns execution, approval, session policy, and tool visibility. JunQi Desktop consumes the same `tools.effective` and `tools.invoke` contracts used by Chat. The plugin never exposes an arbitrary command runner.

Every business call requires an explicit DWS profile in `<corpId>:<userId>` form. Before execution, the plugin reads the complete current DWS leaf schema, retains only the callable parameter and constraint projection, and fails closed if `availability` is absent or not `available`, or if the canonical path, CLI path, effect, risk, confirmation, or idempotency contract differs from the reviewed tool specification.

Every ordinary business read also requires the runtime result to contain the official unified `ok=true`, `outcome=success`, and explicit `data` fields before OpenClaw can receive a successful tool result. A zero-exit pending, failure, or malformed envelope throws a stable sanitized runtime error instead of being wrapped as `success: true`. The long-lived event consumer is intentionally separate because its official transport is ready-marked flattened NDJSON rather than the one-shot JSON envelope.

DWS scalar string parameters must remain strings at the plugin boundary. String-list parameters are represented as arrays in the leaf schema but parsed as CSV by the CLI. The plugin validates required and CLI-required fields, scalar, number, object and string-list types, enum members, known date, date-time and JSON formats, format alternatives, and the official mutually-exclusive, require-one-of and require-together groups before starting DWS. Hidden compatibility parameters are projected away only when the remaining callable constraint is still satisfiable. Interface arrays carried by a string CLI flag validate every CSV member. Natural-language `required_when` text is retained as evidence but is not guessed by the generic parser; the currently registered instances belong to rich-media chat parameters that the narrow text-send policy rejects.

Write tools require an OpenClaw plugin approval. Only `allow-once` and `deny` are offered. Before the approval is requested, the plugin validates the exact Profile, verifies the current DWS leaf Schema, validates the complete callable parameter contract, and confirms that both approval-summary and reconciliation policies exist. Each of the 13 side-effect tools has a bounded approval summary with its stable target, material changes, and a SHA-256 binding for the complete argument object. Report bodies, approval form values, calendar descriptions, and complete approval requests are represented by length and the complete-argument digest instead of being copied into notification text. When the verified DWS leaf also requires confirmation, `--yes` is appended only after OpenClaw grants the approval.

Every registered `write` or `destructive` tool must also appear in the plugin's explicit reconciliation registry. The invocation path checks this registry before resolving the target leaf schema or starting DWS. A future side-effect tool without a reviewed reconciliation strategy therefore fails closed before it can change DingTalk data.

Calendar, Todo, and keyword-matched approval writes require the official DWS Shortcut `ok/outcome/data` envelope and its `verified=true` evidence. Report submission and the remaining approval writes consume official atomic responses and perform a fixed same-ID detail read after the command. The result distinguishes fully verified writes, writes whose target can be observed but whose terminal postcondition is not formally declared, and unknown results. Missing IDs, missing verification evidence, readback failures, or identity mismatches never trigger an automatic replay.

Configuration:

- `dwsPath`: optional absolute DWS executable or verified npm `bin/dws.js` path. JavaScript entries run through the current Gateway Node.js runtime. If omitted, the plugin resolves `PATH` and rejects ambiguous matches.
- `timeoutMs`: command timeout from 1 to 120 seconds. Default: 30 seconds.
- `maxOutputBytes`: combined bounded output limit from 64 KiB to 8 MiB. Default: 2 MiB.
- `eventProfile`: optional exact `<corpId>:<userId>` identity for long-lived event subscriptions.
- `eventSubscriptions`: up to eight reviewed event groups. An empty array disables the event runtime. One group cannot mix IM target classes, OA, Todo, or VoIP. User and group targets are required only for the EventKeys that officially require them.
- `eventBufferSize`: number of event payloads retained in memory for the current Gateway lifecycle, from 1 to 200. Default: 100.

The event runtime is registered only during full OpenClaw activation. Before creating any subscription it verifies the target DWS `event.consume` leaf contract, then waits for the exact official ready marker. It reads flattened NDJSON continuously and requires every accepted payload to contain the official non-empty `type` matching one of that consumer's requested EventKeys. Missing or cross-subscription types are rejected without entering the event cache or Gateway notification path. Accepted events are deduplicated by the stable event identity, emit the OpenClaw-local event name `events_changed`, and remain available through the bounded `junqi_dingtalk_event_snapshot`. OpenClaw publishes that invalidation on the wire as `plugin.junqi-dingtalk.events_changed` with `revision`, `eventType`, an opaque runtime-generation UUID, and a SHA-256 digest of the complete normalized event configuration. Operator clients reread a closed, payload-free status projection through `junqi.dingtalk.events.snapshot`, registered explicitly with `operator.read` and `profileAccess: required`. The operator snapshot is limited to 20 event metadata rows and does not expose event IDs or business payloads. Clients must bind a response to the same attested Gateway connection, runtime generation, complete saved configuration digest, request cursor, and invalidation revision before publishing it. Duplicate or decreasing revisions in one runtime generation are ignored; a replacement generation may restart from revision one. A notification transport failure degrades service health but does not reclassify the accepted DWS payload as an invalid event line. Gateway stop closes stdin first so DWS can cancel subscriptions it created. Event configuration is explicit because starting the service creates or reuses remote personal-event subscriptions.

`junqi_dingtalk_contract_audit` verifies every registered business tool against the target DWS leaf schema with bounded concurrency. It reports every mismatch and does not silently remove or downgrade tools.

The plugin contributes one OpenClaw workflow Skill for daily briefings, meeting planning, Minutes follow-up, knowledge lookup, reviewed report submission, and message or mail drafts. The Skill references only registered `junqi_dingtalk_*` tools, requires the current leaf schema before each business tool, keeps one exact profile throughout a workflow, and preserves partial or unknown write results without replaying them. The dedicated Minutes transcript tool requires one explicit stable task UUID and rejects automatic latest selection, keyword selection, an injected cursor, and single-page mode. A successful result must prove the same task UUID, complete pagination, valid page and paragraph counts, and an object-only paragraph list before it can be used for Todo or report drafting.

The plugin does not store DWS credentials or ordinary tool results. Event payloads are retained only in bounded process memory and are discarded when the Gateway lifecycle ends.

Repository maintainers can run the explicit target preflight with `npm run verify:target-readonly -- --dws-path <absolute-path> --profile <corpId>:<userId> --scope core`. The required `core` scope checks current-user, today-calendar, overdue unfinished Todo, due-today Todo, and pending-approval reads without making unrelated business permissions a prerequisite for Calendar or Todo acceptance. Selecting `--scope extended` runs those five reads plus latest Minutes, Wiki spaces, latest report, mail triage, unread chats, recruiting jobs, and current-user goal rules. Every selected leaf is verified before its invocation, and every read must return the official unified `ok=true`, `outcome=success` envelope with a present `data` field. A zero-exit failure, pending, or malformed envelope is a sanitized per-tool failure rather than a pass. The report retains the selected scope, tool names, counts, and sanitized failures but discards all business payloads. A successful command proves invocation only; it does not prove a non-empty business result unless the current official result contract declares that distinction. This preflight proves only DWS target identity, transport, schema, and the selected read permissions; the OpenClaw Gateway, Agent authorization, Skill routing, writes, events, and user-visible workflow still require their separate acceptance steps.

The same-task Minutes acceptance is `npm run verify:target-minutes -- --dws-path <absolute-path> --profile <corpId>:<userId> --acknowledge-sensitive-read minutes-readonly-same-task < controlled-minutes-fixture.json`. Standard input must be exactly `{ "query": "<controlled-query>", "taskId": "<stable-taskUuid>" }`. Before reading tenant data, the runner verifies all four search, detail, transcript, and action-item leaf schemas and validates every planned argument. Search must be complete and return exactly one result with the expected task UUID; detail must return the same UUID, complete artifacts, and no artifact failure; transcript must prove the same UUID and complete pagination; action items must expose one of the official explicit action arrays. The command stops after the first read-stage failure and reports only stages and counts. It does not retain the query, task UUID, Profile, transcript, artifacts, or action payload. The current action-item result has no formal returned task UUID, so its same-task binding comes from the exact validated command argument and the preceding detail and transcript identity proofs, not from a response identity field. A pass proves only this direct DWS read chain, not OpenClaw routing, a non-empty action list, Todo creation, report submission, or tenant-wide permissions.

The four higher-sensitivity domains have a separate fixture-driven acceptance command: `npm run verify:target-sensitive-readonly -- --dws-path <absolute-path> --profile <corpId>:<userId> --acknowledge-sensitive-reads aitable-contract-recruit-goal-readonly-17 < controlled-sensitive-fixture.json`. The input JSON must contain exact `aitable`, `contract`, `recruit`, and `goal` objects. AI Tables require `query`, `baseId`, `tableId`, and `recordId`; contracts require `projectId`, `projectCode`, `subjectId`, `subjectName`, `analysisRequest`, `reviewTaskId`, and `reviewType`; recruiting requires `jobId`; goals require `templateKeyword`, `ruleKeyword`, `templateId`, and `submitState`. The runner rejects unknown or missing fields before DWS resolution. It verifies all 17 leaf schemas and validates every command before the first business read. Lists are restricted to one item where the contract supports a bound, record and job reads use exact fixture IDs, contract projects use `scope=self`, and contract analysis JSON is forwarded through bounded stdin instead of process arguments or a temporary copy. The OpenClaw contract-analysis tool likewise accepts only a non-empty inline JSON object in `arguments.file`; it rejects local paths, extra fields, non-JSON values, and inputs larger than 1 MiB before replacing the DWS argument with `--file -`. Every read also requires the official unified success envelope; malformed or zero-exit failure results stay in the complete sanitized permission matrix. The result contains only counts, stages, tool names, canonical paths, and sanitized errors; fixture values and business payloads are not retained. This acceptance is intentionally separate from `core`, because missing sensitive-domain permissions must not block Calendar or Todo testing.

The repository-level target Gateway acceptance for the same 17 reads is `corepack pnpm dingtalk:gateway:target-sensitive-readonly -- --gateway-url <ws-or-wss-root> --openclaw-package <absolute-openclaw-package-json> --dingtalk-package <absolute-junqi-dingtalk-package-json> --acknowledge-target-sensitive-readonly JUNQI_DINGTALK_TARGET_GATEWAY_SENSITIVE_READONLY_17 < controlled-gateway-sensitive-input.json`. Standard input must contain exactly `agentId`, `sessionKey`, `profile`, and `fixture`. The command first projects the internal Schema tool and all 17 business tools through `tools.effective`, then invokes the Schema tool for every leaf and validates every bounded argument before the first business read. Any projection, Schema, or argument failure leaves the business-read count at zero. Reads run sequentially only after complete preflight, and each returned Schema digest must equal its preflight digest. Evidence excludes the token, Session, Profile, fixture, and business payloads. This command proves neither authenticated Profile synchronization nor target-tenant field semantics without a real target execution.

The direct event acceptance command is `npm run verify:target-event -- --dws-path <absolute-path> --profile <corpId>:<userId> --event-key <one-reviewed-event-key> --wait-seconds <5-300> [target flags] --acknowledge-subscription event-consume-and-wait`. Target flags are `--user` or `--open-dingtalk-id` for user-scoped IM events, `--group` for group-scoped IM events, and `--role-types creator,executor,participant` for Todo events; the runtime's closed configuration validator rejects incompatible combinations. The command verifies the current consume contract, waits for the exact ready marker, requires a real event whose validated type and sequence match the emitted invalidation, and verifies clean process shutdown. `ready_no_event`, invalid output, startup failure, and unverified shutdown all exit unsuccessfully. Its report contains only counts, the contract digest, sequence, event type, and sanitized errors; Profile, subscription IDs, event IDs, and payloads are discarded. A pass proves the direct plugin runtime boundary only. Real OpenClaw prefixing, operator delivery, desktop connection binding, snapshot reread, Gateway restart, disconnect behavior, and target DWS remote subscription cleanup retain separate acceptance gates.

Repository maintainers can run `corepack pnpm dingtalk:gateway:smoke` from the repository root to install the fixed plugin archive into a disposable pinned OpenClaw Gateway. The smoke does not read host OpenClaw state or configure a DWS path, Profile, or event subscription. It requires an explicit `operator.read` client to return the closed disabled snapshot, an `operator.write`-only client to receive the structured missing-scope rejection, no DWS child process, and a new runtime generation after Gateway restart. This baseline does not prove the authenticated Profile gate, target-tenant permissions, DWS operations, or Gateway event delivery.

Maintainers can run the destructive calendar acceptance with `npm run verify:target-calendar -- --dws-path <absolute-path> --profile <corpId>:<userId> --title <unique-test-title> --updated-title <different-test-title> --start <RFC3339> --end <RFC3339> --timezone <IANA-zone> --acknowledge-writes calendar-create-update-cancel`. The exact acknowledgement is mandatory. Before any write, the runner verifies all three current DWS leaf contracts, validates every argument, and executes the five `core` read-only checks against the same DWS executable and exact Profile. A failed read check produces the complete sanitized preflight matrix and leaves the write count at zero. It then creates one synthetic event, updates the title under the returned eventId, and cancels that same event. Every step requires `verified=true` and the exact same eventId. An unknown create stops without retry and must be investigated by the unique title. An unknown update or cancel stops without another write and returns the known eventId for manual inspection. Successful completion proves the direct DWS calendar Shortcut lifecycle only; Gateway approval, Agent policy, desktop projection, and other business domains retain separate acceptance gates.

The controlled Todo acceptance is `npm run verify:target-todo -- --dws-path <absolute-path> --profile <corpId>:<userId> --executor <same-userId> --title <unique-test-title> --updated-title <different-test-title> --acknowledge-writes todo-create-update-complete-reopen-complete`. The executor is mandatory and must equal the user component of the exact Profile, so this test cannot assign work to another employee. Before any write, the runner verifies the four create, update, complete, and reopen leaf contracts and executes the same five `core` read-only checks under the exact Profile. A failed read check returns the complete sanitized preflight matrix and prevents every write. The runner then creates one self-assigned synthetic Todo, updates the title, completes it, reopens it, and completes it again so the successful terminal state is done. Every receipt must carry `verified=true` and the same taskId. An unknown result stops the chain without replay; a known taskId is returned for manual inspection. The completed test record remains in DingTalk history, and this direct DWS acceptance does not prove Gateway approval, Agent policy, desktop projection, or other business domains.

Approval acceptance begins with the read-only fixture preflight `npm run verify:target-approval -- --dws-path <absolute-path> --profile <corpId>:<userId> --process-code <processCode> --dept-id <departmentId> --form-values '<JSON-string-map>'`. The preflight supports only the official simple form mode. Before reading tenant data it verifies the current form-schema, forecast, create, detail, and revoke leaf contracts and validates the planned arguments. It then reads the exact form schema and forecasts the proposed route; both reads require a unified success envelope, and their business payloads are discarded from the report. It never creates, approves, rejects, or revokes an instance. `ready_for_manual_review` means only that the fixture reached the two official read contracts; the operator must still inspect the form and forecast through the reviewed OpenClaw tools, confirm any selectable approver nodes, and approve the actual write separately. There is no generic write acceptance runner because the official revoke contract does not prove a terminal state and arbitrary templates cannot be assumed safe to create or clean up.

Report acceptance begins with the read-only fixture preflight `npm run verify:target-report -- --dws-path <absolute-path> --profile <corpId>:<userId> --template-name <exact-name> --contents '<JSON-array>' --to-user-ids <userId1,userId2>`. Before reading tenant data it verifies the current template-search, template-definition, submit, and detail contracts and validates the proposed contents and recipients against the fixed CLI subset. It searches by name, requires one exact-name template with one stable templateId, and reads that template definition through a unified success envelope. It rejects malformed, failed, pending, or ambiguous results, empty or duplicate recipients, invalid field types, arbitrary files, chat delivery, and extra command modes. It never submits a report and never returns the Profile, template identity, contents, recipients, or template payload. `ready_for_manual_review` means only that the two reads and the planned submit arguments reached their reviewed contracts; the operator must still compare every content item with the returned template definition and separately approve the actual report write. Automatic submission is intentionally absent because reports cannot be safely deleted by the current reviewed contract.

The fixed agent surface contains 81 business tools and 4 internal tools. The plugin also exposes one payload-free operator event snapshot RPC for the desktop. Its reads include daily calendar, overdue unfinished and due-today Todo, pending approval, meeting availability and attendees, searchable AI Minutes with same-task complete transcript evidence, documents, Wiki, report templates and entries, mail, unread chats, mentions, message search, message send status, exact message lookup, AI Tables, contracts, recruiting jobs, and goal management. The meeting lifecycle can create, update, and cancel one stable event through official DWS Shortcuts with authoritative readback. Destructive calls share the same uncertain-side-effect handling as writes: a timeout, cancellation, or unavailable result never becomes a safe retry. The four higher-sensitivity domains currently expose read-only operations; their writes remain absent. HRbrain tools are not registered because every reviewed HRbrain Shortcut in the current official DWS mainline reports `availability=unavailable`; they remain unavailable until an upstream contract becomes available and passes the same review. OpenClaw can combine these fixed reads with reviewed Calendar, Todo, approval, report, and narrow current-user chat writes in one session; JunQi does not create a separate local task, report, draft-delivery, or scheduling model.

Report submission is available only after the exact draft, template, fields, and recipients have been reviewed. The plugin accepts inline `contents` only, enforces the runner's 1 MiB input bound before approval, and invokes the official `--contents -` mode so the report body travels over standard input instead of the process argument list. Arbitrary `contents-file` paths are rejected. The write is reconciled through the returned reportId and a fixed report-detail read, but remains `succeeded_unverified` because the formal detail contract does not prove every submitted field and recipient.

Chat send is restricted to the official current-user leaf. JunQi accepts only one stable group ID or openDingTalkId, text content, an optional title and AI tag, and a mandatory operation-specific idempotency key. OpenClaw approval displays the exact profile, target, body, and key. Bot, webhook, name-based resolution, batch, mention, file, and media paths remain absent. An asynchronous receipt is queried through the official status leaf and the resulting message ID is read through `chat +messages-mget` with optional enrichment disabled. The plugin requires complete base-message evidence, exact counts, empty failure and missing lists, the exact message ID, and the expected group conversation ID. A pending task or failed lookup remains `unknown`; a matching message stays `succeeded_unverified` because the formal read contract does not prove the complete submitted body and recipient postcondition. The write is never replayed for reconciliation.

Mail send tools remain intentionally absent. The agent can compose mail drafts in the OpenClaw conversation from read evidence, but a user must copy or send them through a separately reviewed future write path.
